Security & RLS

MyQuest uses a three-layer security model: frontend role gating, API-level role enforcement, and Supabase Row Level Security. This page documents each layer, the RLS policies in effect, and the rules for keeping them consistent when making changes.

Never expose SUPABASE_SERVICE_KEY to the client. It bypasses all RLS and has full database access. It must only ever exist in Cloudflare Function environment variables.

Three-Layer Model

LayerWhereWhat it enforces
1. Frontend gating auth.js, data-min-role attributes Hides nav items and entire pages below the required role. Redirects invited-status users to onboarding. Redirects unauthenticated users to login. This is UX only — not a security boundary.
2. API enforcement /functions/api/*.js Every function verifies the Bearer JWT, fetches the caller's role, and returns 401/403 before doing anything. Owner-only fields are gated server-side regardless of what the client sends. This is the primary security boundary for writes.
3. Database RLS Supabase PostgreSQL Blocks direct client-side writes to sensitive tables. The service key (used by Functions) bypasses RLS. Authenticated user JWTs are subject to RLS policies. This is the backstop against console-level attacks.

Layer 1 is not a security boundary. A user who inspects the page source can see hidden elements. Security must be enforced at layers 2 and 3. Layer 1 is purely for usability.

RLS: profiles table

RLS is enabled. Migration: 20260628_rls_security_hardening.sql

OperationPolicyReasoning
SELECT All authenticated users auth.js loads all profiles at login for the in-memory store (team availability, staff dropdowns). Restricting this would break the store for all users. Sensitive fields are protected at the API and query level instead.
INSERT Service role only (no policy) New profiles are created via /api/create-account using the service key.
UPDATE Service role only (no policy) All profile updates go through /api/update-profile. This prevents a staff member from directly setting role='owner' or status='active' via the Supabase client.
DELETE Service role only (no policy) Account deletion goes through /api/delete-account which also removes Storage files and the auth user.

Why SELECT is open

Supabase does not support column-level RLS. A restrictive SELECT policy (e.g. own row only) would break auth.js's store load without a significant refactor to route all profile reads through the API. The sensitive field protection instead relies on:

  • auth.js selecting only id, name, email, role, status, colour, phone, mobile, profile_photo_url, availability, start_date — HR fields are never in the store
  • /api/get-staff-profile returning different field sets based on caller role (owner vs self)
  • staff.html being owner-only, so the HRIS expand card (which fetches full HR data) is never accessible to staff

Owner / ManagerAny file in staff-documents

Storage path conventions

  • Profile photos: {userId}/profile-photo.{ext} — staff manage their own
  • Compliance docs: {userId}/{docType} with no file extension (e.g. {userId}/police_check) — admin-upload only. No extension means replacing a doc always overwrites the same key, so no orphaned files accumulate.

API field security tiers

/api/update-profile and /api/get-staff-profile enforce field-level access based on the caller's role. These tiers are defined server-side — the client cannot bypass them.

update-profile field tiers

TierWho can setFields
Any authenticated user (own profile) Self, manager, owner name, phone, mobile, colour, start_date, address, suburb, state, postcode, residential_address, emergency_contact_*, profile_photo_url, availability, onboarding_complete, agreement timestamps
Owner only Owner role, cleaning_level, status, hr_notes, police_check_url, drivers_licence_url, right_to_work_url, employment_agreement_url, employment_agreement_received_at

get-staff-profile field sets

CallerField set returned
Owner (viewing any staff member) All fields including hr_notes, all doc URLs, employment_agreement_received_at, all agreement timestamps, cleaning_level
Staff member (viewing own profile) Identity, contact, address, emergency contact, profile_photo_url, onboarding_complete only. No HR notes, no compliance doc URLs.

Client-side query rules

Direct Supabase client queries (using the user's JWT) must follow these rules:

  • Never use select('*') on profiles or any table containing sensitive data. Always list specific columns.
  • Never select HR fields client-side: hr_notes, police_check_url, drivers_licence_url, right_to_work_url, employment_agreement_url, employment_agreement_received_at must never appear in client-side queries.
  • Sensitive reads go through the API: Use POST /api/get-staff-profile — it enforces role-based field filtering server-side.
  • No direct writes from client JS to profiles, quote_requests, or company_settings. All mutations go through /functions/api/*.

Change checklist

Run through this when making any security-relevant change:

Adding a field to profiles

  1. Write a migration: supabase/migrations/YYYYMMDD_description.sql with ADD COLUMN IF NOT EXISTS
  2. Decide the tier: should staff be able to set/read this? → place in correct tier in update-profile.js and get-staff-profile.js
  3. Update docs/database.html — profiles table + migrations log
  4. If needed for the store: add to the column list in auth.js (both fast and slow path queries)
  5. Update this page if the security model changes

Adding a new API endpoint

  1. Verify JWT → fetch caller role → check minimum role → return 401/403 before any data access
  2. Use service key for all DB writes
  3. Never trust userId from the request body for permission checks — derive from the verified JWT
  4. Add the endpoint to docs/api-functions.html and its TOC

Changing storage access

  1. Update the policy in a new migration file
  2. Update the storage section in docs/database.html and this page
  3. Test both the staff path and the owner/manager path
