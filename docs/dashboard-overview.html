Dashboard: Overview & Auth

The internal staff dashboard at /dashboard/. Every page is gated behind Supabase authentication. This page covers the overall layout, the script loading pattern, the auth system, and the role model.

Layout Structure

Every dashboard page shares the same shell layout:

<body class="dash-body" data-page="<page-slug>">

  <!-- Mobile top bar (logo + hamburger) -->
  <div class="dash-mobile-bar"> ... </div>

  <!-- Sidebar backdrop for mobile -->
  <div class="dash-sidebar__backdrop" id="dash-backdrop"></div>

  <div class="dash-shell">
    <!-- Sidebar -->
    <aside class="dash-sidebar" id="dash-sidebar">
      <!-- Logo, nav links, user info, logout -->
    </aside>

    <!-- Main content -->
    <div class="dash-main">
      <div class="dash-content">
        <!-- Page-specific content -->
      </div>
    </div>
  </div>
</body>

Sidebar nav links

Each nav link has a data-page attribute matching its target page slug. ui.js compares these to document.body.dataset.page and adds .is-active to the matching link on load.

Some nav links also carry data-min-role="manager" or data-min-role="owner". auth.js hides these via display:none for users below the required role.

Sidebar user footer

The user's initials avatar (.js-user-avatar), display name (.js-user-name), and role (.js-user-role) are populated by auth.js after the session loads. The Logout button (.js-logout) calls signOut() and redirects to login.

Script Loading Order

Every dashboard HTML page loads scripts in this exact order. Order matters — each module depends on the previous ones being available on window.MQ. 

<!-- In <head>, no defer — blocking -->
<script src="js/supabase.js"></script>       <!-- Supabase CDN lib → window.supabase -->
<script src="js/supabase-client.js"></script> <!-- Creates MQ.supabase client -->
<script src="js/store.js"></script>           <!-- Creates MQ.store (in-memory cache) -->
<script src="js/auth.js"></script>            <!-- Auth check; fires mq:ready when done -->

<!-- In <body>, deferred -->
<script src="js/ui.js" defer></script>        <!-- Shared UI utilities -->
<script src="js/<page>.js" defer></script>   <!-- Page-specific logic -->

auth.js must not be deferred. It runs synchronously in <head> to start the session check before the DOM is even parsed. Deferring it would allow the page to render before auth is confirmed.

Auth Flow — auth.js

auth.js is the gatekeeper for every dashboard page. On every page load it:

  1. Checks sessionStorage for a cached mq_session
  2. If found and valid → fast path
  3. If not found or invalid → slow path
  4. On either path, populates MQ.session, gates the UI by role, and fires mq:ready

Onboarding redirect

If the logged-in user's profile has status === 'invited' and their role is not owner, they are redirected to onboarding.html instead of the requested page. This ensures new staff complete the 5-step onboarding before accessing the dashboard.

Data fetched on auth

Auth.js loads on every page load (fast or slow path):

  • All profiles — synced into MQ.store.staff and MQ.store.accounts
  • Company settings (rates, checklist_template, message_of_week) — synced into MQ.store.rates and MQ.messageOfWeek

This means page-level JS can call MQ.store.staff.getAll() synchronously inside mq:ready handlers without an extra Supabase fetch for staff data.

Checking roles in code

// Check if current user has at least the given role
MQ.hasRole('manager')  // true for manager + owner
MQ.hasRole('owner')    // true for owner only

// Example usage
if (MQ.hasRole('manager')) {
  renderAvailabilityWidget();
}

HTML role gating

<!-- Hidden automatically by auth.js for roles below "manager" -->
<a href="clients.html" data-min-role="manager">Clients</a>

<!-- Hidden for roles below "owner" -->
<div class="stat-card" data-min-role="owner"> ... </div>

Client-side gating is UX only. Never rely on data-min-role or MQ.hasRole() as a security boundary. All sensitive operations are gated server-side in the Cloudflare Functions.

Session Lifecycle

sessionStorage: mq_session

{
  "id":           "uuid",
  "email":        "jane@example.com",
  "name":         "Jane Smith",
  "role":         "manager",
  "loginTime":    "2026-06-25T09:00:00.000Z",
  "lastActivity": "2026-06-25T09:45:12.000Z"
}
  • Written on login (via login.js) and refreshed on each page load via auth.js slow path
  • Read on every page load as the fast-path cache
  • lastActivity is updated on mouse/keyboard/touch events (throttled — updated in sessionStorage only)

Idle timeout

A setInterval runs every 60 seconds and checks if Date.now() - lastActivity > 30 minutes. If idle, it calls sb.auth.signOut() and redirects to login.

bfcache (back/forward cache)

auth.js listens for pageshow with event.persisted === true (bfcache restore). It re-validates the Supabase session and fires mq:pageshow so page scripts can reload data without a full navigation.

The mq:ready Event

All page-level JS waits for auth to complete before rendering. The pattern is: 

document.addEventListener('mq:ready', async function () {
  // Safe to call MQ.session, MQ.hasRole(), MQ.store.*
  await loadPageData();
  renderPage();
});

// Also handle bfcache restores:
document.addEventListener('mq:pageshow', function () {
  reload();
});

After mq:ready fires

auth.js patches document.addEventListener so that any code that calls addEventListener('mq:ready', fn) after the event has already fired will still have fn called asynchronously (via setTimeout(fn, 0)). This means it's safe to register mq:ready handlers at any time.

The alternative imperative API:

MQ.onReady(function () {
  // Called immediately if already ready, otherwise queued
});

Realtime Subscriptions

Several pages subscribe to Supabase Realtime channels for live updates. They are set up inside the mq:ready handler, after the initial data load. 

MQ.supabase
  .channel('home-realtime')
  .on('postgres_changes',
    { event: '*', schema: 'public', table: 'quote_requests' },
    function () { reload(); }
  )
  .on('postgres_changes',
    { event: '*', schema: 'public', table: 'profiles' },
    function () { if (MQ.hasRole('manager')) renderAvailability(); }
  )
  .subscribe();

Adding a New Dashboard Page

Checklist for adding a new page to the dashboard:

  1. Copy an existing .html file from /dashboard/ as a starting point
  2. Update data-page="your-page-slug" on the <body> tag
  3. If role-restricted, add data-min-role="manager" to the body and to the nav link
  4. Add a nav link to the sidebar in every dashboard HTML file
  5. Create /dashboard/js/your-page.js with an IIFE listening for mq:ready
  6. Load it as the last <script defer> in the HTML file
  7. Bump the ?v= suffix on any shared files you modified

Nav must be updated everywhere. The sidebar nav is duplicated in every HTML file (there's no server-side include). If you add a nav item, update all dashboard pages.
