Architecture

MyQuest is a serverless, no-build-step web application. Static HTML/CSS/JS is served from Cloudflare Pages; business logic runs in Cloudflare Functions (Workers); data lives in Supabase.

Tech Stack

Frontend

  • Plain HTML5, CSS3, vanilla JS (ES2020)
  • No framework, no bundler, no build step
  • Plus Jakarta Sans (Google Fonts)
  • All JS in IIFEs ((function(){...})())
  • Global namespace: window.MQ

Hosting

  • Cloudflare Pages — static file CDN
  • Cloudflare Functions — serverless Workers for API routes
  • Cloudflare Turnstile — bot protection on public forms
  • Custom domain: myquest.au

Backend

  • Supabase — PostgreSQL database
  • Supabase Auth — JWT-based authentication
  • Supabase Realtime — live data subscriptions
  • Supabase Storage — staff document uploads
  • Resend — transactional email delivery

Tooling

  • Wrangler CLI for local Pages dev
  • Supabase CLI for migrations
  • No test suite currently
  • No CI/CD pipeline (manual deploy via git push to Cloudflare Pages)

Dashboard data reads

Dashboard pages read data directly from Supabase via the JS client — they don't go through Cloudflare Functions for reads. The Supabase anon key is embedded in supabase-client.js; Row Level Security policies control what each user can see.

JS page code
→
MQ.supabase.from('table')
.select()
→
Supabase REST API
JWT in header
→
PostgreSQL
(RLS applied)

Write path always goes through Functions. Direct client-side writes to sensitive tables are blocked by RLS. All mutations go through /api/* Functions which use the service key (bypasses RLS) after verifying the caller's JWT and role.

Hosting & Deployment

The repo is connected to Cloudflare Pages via Git integration. Pushing to main triggers an automatic deploy. There is no staging environment — main is production.

  • Static assets are served directly from Cloudflare's CDN edge nodes.
  • Functions in /functions/api/ are deployed as Cloudflare Workers alongside the static site.
  • Reminder Worker (/reminder-worker/) is a separate Cloudflare Worker deployed independently via wrangler deploy in that directory. It runs on a cron trigger (daily 9pm + every 30 minutes).
  • The _headers file in the root configures Cloudflare response headers (CSP, cache rules, etc.).

Local Development

What you need to run the site locally

There are two ways to run MyQuest on your computer, depending on what you're working on:

MethodCommandWhat worksWhat doesn't
Simple (pages only) python3 -m http.server 8788 All HTML pages, CSS, JS, dashboard UI Any /api/* call (login actions, saving data, etc.)
Full (pages + API) npx wrangler pages dev . --port 8788 Everything — pages and API functions Requires .dev.vars to be set up first (see below)

The dashboard always connects to the live Supabase database even when running locally. There is no separate test database.

Setting up .dev.vars (one-time setup)

Think of .dev.vars as a private notepad that sits on your computer only. It tells the local API functions your secret keys — the same keys that are stored securely in Cloudflare for the live site. Without it, API calls will fail locally because the functions won't know how to connect to Supabase, send emails, etc.

How to set it up:

  1. In the project root, duplicate the file .dev.vars.example and name the copy .dev.vars
  2. Open .dev.vars and replace each placeholder with your real key
  3. Save the file — that's it. Wrangler picks it up automatically next time you run it

.dev.vars is never committed to git. It's in .gitignore. This is intentional — it contains your real secret keys. Never upload or share this file. The .dev.vars.example file is the safe committed version with placeholder values.

Where to find each key:

Cache Busting & Versioning

There is no asset fingerprinting. Instead, cache-busting is done by updating ?v=YYYYMMDD query strings on <link> and <script> tags whenever a file changes. 

<link rel="stylesheet" href="css/dashboard.css?v=20260814">
<script src="js/auth.js?v=20260809" defer></script>

When editing a shared file (e.g. style.css, auth.js), bump the version suffix on every page that loads that file. The version.txt file in the root is a human-readable record of the last deploy version.

Security Model

Authentication

  • Supabase Auth issues JWTs on login. JWTs are stored in localStorage (managed by Supabase JS client) and the decoded session is cached in sessionStorage as mq_session.
  • All dashboard pages call auth.js (no defer) which verifies the session before the DOM loads. Unauthenticated users are redirected to login.html.
  • Idle timeout: 30 minutes of inactivity signs the user out.

Authorisation

  • Client-side role gating: data-min-role attributes on HTML elements hide UI that the user's role doesn't permit. This is a UX convenience only — not a security boundary.
  • Server-side role checks: Every Cloudflare Function independently verifies the caller's JWT, fetches their role from Supabase, and rejects requests below the required level. This is the actual security enforcement.
  • Supabase RLS policies prevent direct client-side reads of sensitive data by lower-privilege users.

Secrets

  • The Supabase anon key is intentionally public — it's embedded in supabase-client.js. Security relies on RLS, not key secrecy.
  • The Supabase service key is secret and lives only in Cloudflare's encrypted environment variables. It is never exposed to the browser.

CORS

All API functions set Access-Control-Allow-Origin: https://myquest.au — only requests from the production domain are accepted. The OPTIONS preflight handler is implemented on each function.

Spam protection

  • The public quote form uses Cloudflare Turnstile (sitekey embedded in HTML, secret verified server-side in submit-quote.js).
  • The login form also uses Turnstile.
